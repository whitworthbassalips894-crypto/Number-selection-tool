# 概率与产品评审 · 特码智能选号助手

> 评审方式：把 `index.html` 内联引擎抽出来，在真实底库（1786 期可用）上做逐期回放 + 统计检验。
> 全部数字可用 `node scripts/probability-audit.mjs`（默认最近 500 期）或 `--all`（1486 期）复算，不修改任何业务代码。

---

## 一、结论先说（TL;DR）

| 维度 | 结论 |
| --- | --- |
| 概率层面 | **没有可提取的预测信号。** 综合评分 AUC = **0.501**（0.5 = 完全无预测力），三组 7 码与综合前 5/7/10/12 码命中率全部落在 `k/49` 基线的一个标准误内。这不是"策略还不够强"，而是特码本身是独立均匀抽样——**任何权重调参都不会改变这个结论**。 |
| 产品层面 | 有 **11 个真实可改的点**，其中 5 个是 P0（会直接误导用户或造成真实体验缺陷），不是"硬说"。 |
| 最值得做的一件事 | 把「决策透明」补上：**每档显示投入成本 / 覆盖率 / 期望亏损**，并把「连错 N 期」「偏冷偏热」这类信号改成按档位归一化的说法。这是唯一能实际提升用户价值的方向。 |

## 二、我做的四项检验与结果

### 1. 特码本身均匀吗？——均匀

```
卡方 χ² = 40.83（df = 48，5% 临界值 65.17）→ 未检出偏差
最高频 49 次 / 最低频 23 次 / 理论 36.4 次（极差属正常抽样波动）
```

底库质量合格（`src/audit.js` 只报出 1 条历史坏行：2022-132 正码 33 重复），**不存在"某些号更容易开"可利用的偏差**。

### 2. 「遗漏越久越该开」成立吗？——不成立

按号码已连续遗漏期数分组，统计下一期开出该号的概率（无记忆理论值恒为 2.04%）：

| 已遗漏 | 实际开出率 | 95% CI |
| --- | --- | --- |
| 0–9 期 | 1.94% | [1.73, 2.15] |
| 10–19 期 | 2.23% | [1.98, 2.48] |
| 20–29 期 | 2.04% | [1.77, 2.31] |
| 30–39 期 | 2.07% | [1.77, 2.37] |
| 40–59 期 | 2.02% | [1.77, 2.26] |
| 60+ 期 | 2.01% | [1.84, 2.19] |

六个区间**全部覆盖 2.04%**。`#2 遗漏回补` 的立论前提（久未开 → 概率上升）在这份数据里不存在。
同理，近 30 期最热 7 码命中 14.75%、最冷 7 码命中 13.95%，与 14.29% 无差异；前半段号码频次与后半段的相关系数 r = **−0.063**（r² = 0.4%，纯噪声）。

### 3. 三策略 + 综合评分有预测力吗？——没有

全量回放 1486 期：

| 选号方式 | 命中 | 命中率 | 基线 | z |
| --- | --- | --- | --- | --- |
| #1 热态 7 码 | 211/1486 | 14.20% | 14.29% | −0.10 |
| #2 遗漏 7 码 | 215/1486 | 14.47% | 14.29% | +0.20 |
| #3 周期 7 码 | 197/1486 | 13.26% | 14.29% | −1.13 |
| 综合前 5 码 | 146/1486 | 9.83% | 10.20% | −0.48 |
| 综合前 7 码 | 219/1486 | 14.74% | 14.29% | +0.50 |
| 综合前 10 码 | 302/1486 | 20.32% | 20.41% | −0.08 |
| 综合前 12 码 | 363/1486 | 24.43% | 24.49% | −0.06 |

**综合评分 AUC = 0.5014**：把"开出的特码"排在另一个随机号码之上的概率是 50.1%，等价于抛硬币。
（最近 500 期是 0.5121，z≈1.75，同样不显著；换窗口就漂移，正是噪声的特征。）

> 顺便：README 里"共识加成让三策略共振号码优先"在数据上也得不到支持——共识号（≥2 组）命中 1.80%（n=1054），非共识号 2.35%（n=6292），理论都是 2.04%。

### 4. 连错之后会回补吗？——不会

`#1 热态` 在连错 ≥1 / ≥3 / ≥5 / ≥8 期之后的下一期命中率：**13.89% / 14.19% / 15.53% / 16.18%**（期望 14.29%），全部在抽样误差内。上期命中后本期命中 16.11%（n=211），上期未中后 13.89%（n=1274），同样无差异。

## 三、真正值得改的东西（按优先级）

### P0-1 「四档严格包含」的承诺被破坏（17.8% 的期数）

README 写明：`[5][7][10][12]` 四档取同一份综合分排序的前 N 码，**档位之间严格包含**。但第 5 档不是截取，而是 `#1∪#2∪#3` 去重后的并集，两者不是同一个集合。

```
全历史 1586 期：12码档 ⊄ 并集档 的期数 247 = 15.6%（平均缺 1.08 个号，最多缺 3 个）
最近 500 期：89/500 = 17.8%
最坏示例：并集只有 16 码，而综合分第 3/5/... 名的 14、2、46 号不在并集里
```

用户操作路径上非常直观的坑：**先点「12码」，再点「并集全取」，号码会变少、还可能丢掉刚看到的高分号**。

建议：两种口径二选一，不要混用——
- A（推荐，改动最小）：把并集档改成 `综合前 12 ∪ 三组并集`，保证单调包含，按钮文案仍显示实际码数；
- B：把并集档明确改成独立的第 5 个「另一种口径」，按钮样式区别于 4 个截取档，并在提示里写清"不是前 N 码的延伸"。

### P0-2 奇偶/大小均衡项有符号 bug（三处复制）

```js
// index.html:1478、src/six-tier.js:135、src/strategy.js:160
val -= 0.05 * Math.abs(oddCnt + isOdd - 3.5) - 0.05 * Math.abs(bigCnt + isBig - 3.5);
```

第二项本该是"大号偏离 3.5 越远越减分"，实际写成了 **`+0.05 × 偏离`——越偏越加分**，与奇偶项方向相反。实测影响：

| | 三组 21 码中大号(≥25) 占比 |
| --- | --- |
| 当前代码 | 48.5% ~ 49.1% |
| 修正后 | 51.2% |
| 理论 | 51.0% |

偏差不大但方向系统性地偏向小号。修法：`- 0.05 * abs(...)` → `+ 0.05 * abs(...)`（即两项都用减号）。
注意：这会改变历史输出，需要同步更新 `tests/tool2-model.test.mjs` 里的固定断言（如并集 12~21 码、具体期号样例）。

### P0-3 温度计阈值不随档位调整 —— 标签在描述"码数"，而不是"状态"

`rate >= 0.30 → 偏热 / >= 0.20 → 正常` 是写死的，但各档真实命中率差异巨大。纯随机下 30 期的标签分布：

| 档位 | 真实命中率 | 偏冷 | 正常 | 偏热 |
| --- | --- | --- | --- | --- |
| 5 码 | 10.2% | **92.1%** | 7.7% | 0.2% |
| 7 码 | 14.3% | 74.9% | 23.0% | 2.1% |
| 10 码 | 20.4% | 40.6% | 45.3% | 14.1% |
| 12 码 | 24.5% | 22.1% | 47.6% | 30.3% |
| 并集(≈18.4 码) | 37.6% | 1.2% | **85.2% 偏热** | — |

也就是说：**选 5 码时系统几乎永远显示"偏冷"，选并集时几乎永远显示"偏热"**，与策略表现无关。而底部基线说明（"7码基线 14.3% · ±12pp"）也没随档位更新，切到 5 码或并集时是错的。

建议：
1. 标签改成基于**相对基线的偏离**：`hits` 与 `Binomial(30, K/49)` 比较，输出"高于/低于随机 X.X 个标准差"或三档分位（如 <15% / 15–85% / >85% 分位）；
2. 基线说明随之动态生成：`K/49`、以及该档 30 期样本的 ±1.96·SE。

### P0-4 「系统参考信号」的三选一存在多重比较

信号逻辑是"挑近 30 期表现最好的那组"，再用 30% 当阈值。纯随机下：

```
单策略 30 期命中 ≥9 期(30%)：2.08%
三选一至少有一个达到：6.1%   → 每次开奖都有 ~6% 概率点亮"表现较好，可优先参考"
```

而 30 期样本本身的 95% 波动带是 ±12.5pp，`14.3%` 与 `30%` 之间的差距完全被噪声吃掉——**这个提示在语义上把一个纯随机事件包装成了"建议"**。
建议：要么删掉"可优先参考"这一档，改成"本期与随机基线无显著差异（附 z 值）"；要么至少加上"三选一"的多重比较校正说明。

### P0-5 「当前连错 N 期」在当前档位几乎恒为橙色，且没有数学含义

`losingStreak` 不区分档位，但连错概率随码数急剧变化。最近 500 期里"处于连错 ≥5 期"的期数占比：

| 档位 | 连错 5 期的单期概率 | 处于"连错≥5"的期数占比 | 连错 ≥10 |
| --- | --- | --- | --- |
| 5 码 | 58.4% | **60.8%** | 35.0% |
| 7 码 | 46.3% | 42.8% | 20.6% |
| 10 码 | 31.9% | 30.4% | 8.8% |
| 12 码 | 24.5% | 23.4% | 6.2% |
| 并集 | 9.5% | 4.0% | 0.0% |

- 选 5 码时，**六成的期数都顶着"已连续 5 期未中，建议谨慎参考"**；
- 30 期窗口内出现一次 5 连错的概率几乎是 100%（各档皆然）；
- 更关键：**连错之后命中率并没有上升**（见第二部分第 4 项），所以"连错"不能作为决策依据。

建议：按档位给 `losingStreak` 定阈值（如 `P(连错 n 期) < 5%` 才提示，5 码档需要 ~28 期），或直接把徽章改成"当前连错 N 期 · 纯随机下此档连错 5 期概率 58%"。

### P1-6 缺成本与期望亏损的显性展示（与"理性娱乐"的宗旨冲突）

各档按「每注 1 元、赔率 48」的数学期望（RTP 恒为 97.96%，与选号方式完全无关）：

| 档位 | 每期投入 | 期望返奖 | 期望净亏 | 命中率 |
| --- | --- | --- | --- | --- |
| 5 码 | ¥50 | ¥49.0 | **−¥1.02** | 10.2% |
| 7 码 | ¥70 | ¥68.6 | **−¥1.43** | 14.3% |
| 10 码 | ¥100 | ¥98.0 | **−¥2.04** | 20.4% |
| 12 码 | ¥120 | ¥117.6 | **−¥2.45** | 24.5% |
| 并集(≈18.4) | ¥184 | ¥180.2 | **−¥3.76** | 37.6% |

页面底部只有一句"请理性娱乐"，但**没有任何地方告诉你"这一档每期要花多少、长期期望亏多少、覆盖率是多少"**。并集档因为码数浮动 15~21（全历史 14~21，平均 18.2），投入也在 ¥150~¥210 之间浮动，用户并不知道。
建议：在每个档位按钮下加一行 `N 注 / 覆盖 K/49 / 期望净亏 ¥x.xx`；并集档额外标"码数随当期浮动"。成本远低于任何新策略，价值最高。

### P1-7 「智能」叙事与数学事实不一致（最大的产品风险）

工具所有可见文案（`智能主推`、`策略同步`、`三策略共振`、`共识加成`）都在暗示存在真实信号。但：
- 综合评分 AUC = 0.501；
- 所有档位命中率 ≈ `K/49`，差异的 z 值全部 < 1.5。

这不是要求删功能——**"一套可复现、无未来函数、有完整回测与边界检查的选号工具"本身就有价值**（随机挑号 + 均衡形态 + 一键复制 + 自动核对），但文案应该与事实对齐：
- 把"智能主推"改成"本期推荐（规则化）"；
- 主推卡片下加一行："本推荐与随机选号的期望回报相同（RTP 97.96%），差异仅在形态分布与可复现性。"
- 保留温度计/连错作为**看板**，但去掉"建议谨慎参考 / 可优先参考"这类决策性措辞。

### P1-8 三份引擎代码复制，改一处要改三处

同一段 `selectBalancedSeven` 逻辑存在于：
- `index.html:1409`（页面真正跑的）
- `src/strategy.js`（Node/测试用）
- `src/six-tier.js`（另一份，带 `WAVE_MAP` 硬编码）

P0-2 的符号 bug 就是**三份都复制了同一个 bug**，说明它们已经发生过同步。并且三份的参数不一致（`src/strategy.js` 的奇偶软约束用了 `size/2`，`index.html` 用硬编码 `3.5`）。
建议：把引擎抽成 `src/engine.js`（浏览器用 `type="module"` 直接 import），`index.html` 只保留 UI；`tests/tool2-model.test.mjs` 改为直接 import 该模块——现在它是靠 `vm` 截取 `<script>` 字符串来测的，任何标签改动都会让测试失效。

### P1-9 约 7000 行死代码被 Service Worker 预缓存

`src/app.js`(1253) + `src/combined.js`(66) + `src/dailyfive.js`(832) + `src/tool1/*`(~2000) + `src/six-tier-app.js`(555) + `src/replay-worker.js` 等，**`index.html` 一个都没有引用**（只加载了 `src/note-sync.js`）。但 `sw.js` 的 `SHELL_FILES` 把它们全部列入安装期预缓存——首次安装要多下 ~250KB，还增加了缓存版本不一致的风险。

判断：这些是历史版本（"工具 1 / 工具 2 / 六档"）的遗留。建议要么明确标记为归档目录（`archive/`，从 `sw.js` 移除），要么接回页面；不要保持"看着在用、其实没跑"的状态。

### P1-10 README 与代码事实脱节

| README 说法 | 实际 |
| --- | --- |
| 完整历史 1780 期有效数据 | 1786 期可用 / 1787 期总量 |
| 内置底库同步至 `2026-320`，共 1781 期 | `2026-326`，1787 期 |
| 并集历史实测 12~21 码，平均约 16.4 码 | 实测 **14~21 码，平均 18.2**（全历史） |
| `[5][7][10][12]` 与并集档"严格包含" | 15.6% 的期数不成立（见 P0-1） |

README 是唯一的行为规格说明，这里的数字偏差会直接导致后续改动按错误假设走。

### P2-11 小处

- `npm ci` 之前 `npm test` 会有 3 个文件因缺 `jsdom` 失败（`smoke` / `rhythm-ui` / `note-sync`），非代码问题但建议在 README 的"开发"段落写清"必须先 `npm ci`"；
- `selectBalancedSeven(scoreMap, {})` 缺少 `opts` 时会在 `opts.oddRange[0]` 抛 TypeError（`src/strategy.js` 有默认值，`index.html` 版本没有）——两个同名函数签名不一致，属于 P1-8 的连带问题；
- 并集档平均 18.4 码 × 每期 1 注 = 每期 18~21 注，若用户误以为"18 码档是固定 18 注"来预算，会有偏差，见 P1-6。

## 四、不建议做的事（避免"硬优化"）

1. **不要为了提升历史命中率继续加策略 / 调权重 / 引入杀号。** AUC = 0.501 意味着评分里没有可提取的信号；任何在 1786 期上"调高"的参数，都是在拟合噪声，换 500 期窗口就会回落（0.5121 → 0.5014 已经演示了这一点）。当前"权重 40/34/26 + 组内加成 + 共识加成"这套结构的自由度远超数据能支撑的量。
2. **不要引入"机器学习预测"**。在 i.i.d. 均匀抽样 + 1786 个样本下，任何模型的样本外 AUC 都会回到 0.5。这会显著增加复杂度而零收益。
3. **不要把"连错回补"做成功能**（如自动加倍）。这是赌徒谬误的工程化，且与页面现有的"严禁倍投追号"自相矛盾。
4. **不要为了"看起来更准"去删掉温度计/连错这些负反馈模块**。它们是这个工具最诚实的部分，应该保留并**校准**，而不是移除。

## 五、如果只做三件事

1. **修 P0-1（档位嵌套）+ P0-2（符号 bug）** —— 两个都是确定性缺陷，改动小、可测；前者用户直接可见，后者让"均衡"名副其实。
2. **给每个档位加"成本 / 覆盖 / 期望净亏"一行** —— 一句话级别的 UI 改动，直接对应"理性娱乐"的产品责任。
3. **把温度计与连错改成"相对基线的 z 值 / 分位"** —— 让看板说人话，同时消除"选 5 码永远偏冷、选并集永远偏热"的假信号；基线文案随档位动态生成。

概率上这个工具没有可优化的空间（数据已经证明），但产品、代码结构与诚实度上有明确的优化空间。
